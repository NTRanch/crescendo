# GDScript / Godot 4 — library & tooling research

**Engine / language:** Godot 4.x (pin one stable for the week; Dialogic 2's current floor is Godot 4.5) · GDScript
**Role in the program:** W6 *Crescendo* — arousal-engine/1 re-implemented **from the spec** in a second engine, with three girls' face sets selectable in the same build. The week is the estate's spec-vs-implementation honesty test: divergence between the GDScript build and the Rust reference is filed as a *spec* finding, and the engine/girl decoupling test (swap the girl → the performance changes, nothing else does) is the week's headline verdict. Godot also matters beyond the jam as the estate's zero-royalty engine option.
**Delivery shape:** web export with a single-file template — the `.pck` embedded into one `index.html`. **Named seam (the fiddliest packaging in the program):** Godot's *standard* web export is a multi-file set (`.html` + `.js` + `.wasm` + `.pck`, per the official export docs: https://docs.godotengine.org/en/4.4/tutorials/export/exporting_for_web.html). There is no one-click single-file export; the jam shape needs a custom HTML shell that inlines the engine wasm and the pack (base64, ~+33% size) or an equivalent loader shim. The W6 preflight proves the template on an empty project *before* any game work starts — that order is program law, not advice.
**Engine licence:** Godot is MIT-licensed, free for any use, no royalties, no revenue thresholds, no splash requirement. This is the cleanest licence in the program and the reason Godot is the estate's hedge engine.

## Parts matrix

### (a) 2D rendering & sprite animation — BUILT-IN, strong

- **Built-in (free, MIT):** `CanvasItem`/`Node2D` rendering with the **Compatibility renderer** (the only renderer the web export supports — Forward+/Mobile do not target web), `AnimatedSprite2D` + `SpriteFrames` for frame animation, `AnimationPlayer` + `AnimationTree` for keyframed everything-else, `GPUParticles2D`, and 2D lights/normal maps in Compatibility. For a VN stage, this is complete out of the box; nothing to buy.
- **Verdict:** built-ins only. The week's presentation weight sits on skeletal rigs (row b) driven by data (register), not on sprite tooling.

### (b) Skeletal / puppet animation — SPINE IS OFFICIAL; CUBISM IS COMMUNITY; DRAGONBONES EXISTS

- **spine-godot (Esoteric Software, official).** Two flavours per the vendor docs (http://EsotericSoftware.com/spine-godot): a **GDExtension** dropped into the project's `bin/` (all platforms Godot supports; AnimationPlayer integration; *no dedicated C# bindings* — irrelevant for a GDScript week) and a **custom C++ engine module** build (full editor integration, requires Esoteric's editor/template builds). **Version discipline is strict:** the runtime's Spine version *and* Godot version must both match the export — a 4.3 extension will refuse 4.2 skeleton data with an import error (worked example, Godot 4.6.1 + spine-godot 4.2, Oct 2026: https://riggyapp.com/blog/godot-spine-animation-from-psd). Licence: Spine editor licence required (Essential US$69 / Professional from US$299 one-time; Enterprise above US$500K revenue) — same licence as the Unity week, which is the point: **one rig, one vendor, both engines.** Maturity: vendor-maintained, current.
- **GDCubism / "Cubism for GDScript" (MizunagiKB's `gd_cubism`) — community, listed by Live2D itself.** Live2D's community-SDK page lists a GDExtension for calling the Cubism SDK from GDScript (Godot 4.1 era) and states plainly that community SDKs are *not* maintained by Live2D and may lag the current Cubism SDK (https://docs.live2d.com/en/cubism-sdk-tutorials/community-sdk/). Building it means compiling the GDExtension against the Cubism Native SDK/framework yourself (SCons; the Cubism Core library itself stays under Live2D's proprietary licence, with the same publication-licence thresholds as Unity: free under ¥10M annual sales for small-scale/general users). **Verdict: exists, verified, and not chosen for W6** — a one-week honesty test cannot also be a native-extension build project. If the estate later wants Cubism *in Godot* for a full game, this is the door, and it is a project, not an addon install.
- **Godot-DragonBones (Daylily-Zeleen) — GDExtension, MIT, Asset Library.** Current v2 line (2.0.2, Godot 4.3+, DragonBones Pro 5.6 data) on the official Asset Library (https://godotengine.org/asset-library/asset/3920). DragonBones' editor is free, making this the zero-cost skeletal route; the ecosystem and tooling polish are a tier below Spine's, and DragonBones is *not* an estate rig format. **Verdict:** credible fallback if Spine licencing ever blocks a Godot title; not the W6 choice.
- **Built-in Skeleton2D** (`Skeleton2D` + `Bone2D` + polygon skinning): genuinely built-in and free, adequate for simple two-bone puppetry, visibly outclassed by all three above for full character rigs. Useful for props and simple articulated set dressing.
- **W6 pick:** spine-godot GDExtension, version-locked (Spine editor version = runtime version = a pinned Godot build), because the decoupling test needs rigs that are *data-swappable* — Spine skins/attachments are exactly that.

### (c) Audio + reactive / voice-event systems — BUILT-IN IS BETTER THAN EXPECTED; FMOD EXISTS; WWIISE IS A DETOUR

- **Built-in (free):** `AudioStreamPlayer` family + the bus system (effects, volume/pitch buses) plus — load-bearing for this design — **`AudioStreamInteractive` / `AudioStreamSynchronized`** (Godot 4.3+): native adaptive-music primitives (clip queues, beat-synced transitions, layered synchronised stems) with no middleware. For a one-build arousal-engine test whose audio needs are tier-boundary stingers and ambient loops, built-ins are *sufficient and honest*.
- **FMOD for Godot — utopia-rise/fmod-gdextension, maintained.** A Godot 4 GDExtension integrating the FMOD Studio API: banks auto-loaded, events exposed to GDScript, `FmodEventEmitter2D/3D` nodes, live update from Studio (https://raw.githubusercontent.com/utopia-rise/fmod-gdextension/master/README.md; current line targets Godot 4.4 / FMOD 2.03). FMOD's own licence applies on top. This is the same audio authoring tool recommended in the Unity chapter — **one FMOD Studio project can serve both engines**, which is the strongest argument for adopting it at full-game scale. For W6 it is optional weight; adopt only if the week's audio design outgrows interactive streams.
- **Wwise for Godot — exists, not recommended here.** The community Wwise integration (Alessandro Famà's, GDExtension-based; listed as targeting Godot 4.3 / Wwise 2024.1 in ecosystem indexes, https://allgodot.com/tags/audio) is real but heavyweight, and its author steers new Godot work toward the FMOD extension. Wwise's free Indie licence (budget < US$250K) is documented at https://blog.audiokinetic.com/free-wwise-indie-license/. **Verdict:** skip for Godot; if Wwise is ever adopted estate-wide it arrives via Unity first.
- **Reactive voice note:** W6 has no voice-coverage system to build (that is W5/Unity); its audio events are engine tier events. The event→sound mapping is a GDScript signal table — custom, trivially, and deliberately identical in shape to the Unity week's bus so the two chapters' findings compare.

### (d) Dialogue / VN frameworks — DIALOGIC 2 (primary, with an alpha warning), INKGD (option)

- **Dialogic 2 — the Godot dialogue standard, MIT, free.** Visual timeline editor, character/portrait management, branching, variables, voice-line hooks, save/load integration, translation export (https://github.com/dialogic-godot/dialogic; docs: https://docs.dialogic.pro/getting-started.html). **Currency, stated honestly:** Dialogic 2 is still formally in **Alpha** — its own documentation warns of workflow breakage between releases, changelogs carry migration notes, and the current line **requires Godot 4.5+**. It is nonetheless the most-used dialogue system in the Godot ecosystem and is actively developed (43 releases). **W6 ruling:** the arousal test needs only a thin script layer (stage directions + a handful of lines), so Dialogic is *available but optional* for W6; for any full Godot VN it is the default pick, pinned to one release for the whole production.
- **inkgd — GDScript port of inkle's Ink (community, MIT-family).** Exists and is maintained as the Ink-in-Godot route for writers already in Ink; no visual editor, no staging — same trade as Ink in Unity. Option for narrative-logic-heavy titles; not needed for W6.
- **NONE / custom for the test harness itself:** W6's "dialogue" is a test script format (cue lists fired at the engine), which is estate tooling, written from scratch (see register) — bending Dialogic timelines into a conformance harness would contaminate the very measurement the week exists to make.

### (e) State machines & save systems — STATE CHARTS ADDON + BUILT-IN SERIALISATION

- **Godot State Charts (derkork/godot-statecharts) — MIT, Asset Library, current (0.22.x line).** Node-based statecharts (compound/parallel/history states) that solve the FSM state-explosion problem, GDScript- and C#-facing, with an editor debugger (https://github.com/derkork/godot-statecharts; install/usage: https://derkork.github.io/godot-statecharts/installation). This is the right *presentation-flow* machine (menus → scene → results).
- **The arousal engine itself is NOT built on it** — see the register: the engine must be a pure, fixed-step, engine-agnostic evaluator so its traces can be diffed against the Rust reference. State Charts orchestrates screens *around* the core; the core stays a plain GDScript class with explicit transition tables. (`AnimationTree`'s state machine is for animation blending — presentation only, same rule as Unity's Animator.)
- **Saves:** built-in and sufficient — `ResourceSaver`/`ConfigFile`/JSON via `FileAccess` to `user://` (on web exports, `user://` persists in the browser's IndexedDB, with the usual browser-eviction caveat). Dialogic 2 ships its own save integration if adopted. No paid save asset exists or is needed in this ecosystem. **Verdict:** custom serialisation of the pure-data core (same schema discipline as the Unity chapter), State Charts for flow.

### (f) UI — BUILT-IN CONTROL SYSTEM, complete

- **Built-in (free):** the `Control` tree (containers, anchors, themes/`ThemeDB`, `RichTextLabel` with BBCode for styled dialogue text, `AudioStreamPlayer`-backed UI sounds) is a complete VN/menu UI kit, and themes are data — an NTRanch house theme (dark ground, hot-pink accent per the estate book style) is a `.tres` theme resource, shared across Godot titles. No UI addon is required; the jam's six required screens (Title / Pause / How to Play / Gameplay / Settings / Game Over-or-Victory) are a State Charts flow over themed Controls.

### (g) Asset pipeline & build-size for web — SMALL ENGINE, CUSTOM SINGLE-FILE SHELL

- **The export, honestly:** Godot web export produces `.html` + `.js` + `.wasm` + `.pck` (docs above). Settings that matter: **Compatibility renderer** (mandatory for web), **single-threaded export** (default since 4.3 — avoids the SharedArrayBuffer cross-origin-isolation headers that itch embeds historically broke on; threaded builds need `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` or the PWA service-worker workaround, per the same docs page), and **custom HTML shell** (the export's shell option) as the vehicle for the single-file shape.
- **Size reality:** Godot's engine wasm is dramatically smaller than a Unity web build (single-digit-to-low-tens of MB class before content, template-dependent), and the `.pck` is the game's own assets with Godot's import compression (lossy/lossless texture compression, Vorbis/Opus audio) applied at import. The single-file penalty is the base64 inflation (~+33%) on wasm+pck — affordable here in a way it is not for Unity, which is itself a W6 finding worth writing down.
- **GDExtension warning for web:** extensions must ship a web build of their native library or the export breaks — spine-godot's GDExtension advertises all-platform support, but the *web template + extension* combination is a named preflight check, not an assumption (see Risks).

### (h) Testing / CI — GDUNIT4 (primary), GUT (established alternative)

- **gdUnit4 (MikeSchulze) — free/MIT-family, current v6.x line built on Godot 4.5** (Asset Library: https://godotengine.org/asset-library/asset/1522). GDScript (and C# via gdUnit4Net) test suites with scene runners, mocking/spies, editor integration, and an official GitHub Action (`gdunit4-action`) for CI. **This is the conformance weapon for W6:** the arousal engine's golden traces (input script → expected tier/culmination/face-state sequence, generated from the spec/Rust reference) run as gdUnit4 suites against the GDScript re-implementation; every mismatch is a filed divergence.
- **GUT (Godot Unit Test, bitwes) — MIT, the older standard.** Fully compatible with Godot 4, CLI runner (`gut_cmdln.gd`) used widely in CI, including by other addons' own test suites. Choose gdUnit4 for new work (scene-runner ergonomics, active v6 line); GUT remains a fine, battle-tested second.
- **CI shape:** headless Godot + gdUnit4-action on GitHub Actions — no licence servers, no activation dance (contrast Unity/GameCI). A Godot week is the cheapest CI citizen in the program.

## Write-from-scratch register

1. **Arousal engine re-implementation FROM SPEC (W6's reason to exist).** *Why from scratch, and why again:* the deliverable is not "an arousal engine that works" — the Rust one works (15/15 on its package tests). The deliverable is *evidence about the spec*: a second implementer (GDScript, from the written spec alone) producing tier timings T1 4+4 / T2 7+6 / T3 11+9 / T4 16+12 s, exactly-once culmination, and F-03/F-05/F-10 coupling that match the reference traces. Where they don't match, the *spec* is ambiguous and gets amended — that amendment list is the port-back. *Rides on:* a pure GDScript class, fixed-step accumulator off `_physics_process`, zero engine services inside the evaluator (no `Time`, no scene tree, seeded RNG injected). Determinism is achievable precisely because the core refuses engine conveniences.
2. **Face-state system (F-codes as data) — the decoupling mechanism.** *Why:* W6's headline test — swap the girl, change the performance, change nothing else — is only possible if a "girl" *is* a face-set data bundle: F-code → rig parameter/animation mapping, blush/gaze channels, coupling gains, all in `Resource` (`.tres`) data consumed by one driver. No addon sells F-codes; the estate's §1.7 full-disc gaze definition and D-4 channel measurements are the spec. *Rides on:* spine-godot animation/skin switching + bone control for gaze, modulate/parameter channels for blush, `AnimationPlayer` for authored expression poses where rigs are sprite-based.
3. **Sex-scene staging / two-body contact.** *Why:* same open problem as every engine (contact/occlusion is research, not product). Godot's contribution to the question: whether `CanvasItem` ordering + rig layers make two-rig staging *cheaper* to author than Unity's render-pass world. *Rides on:* `z_index`/`CanvasLayer` discipline, per-rig drivers, authored `AnimationPlayer` beats.
4. **Lactation / fluid sim.** *Why:* estate simulation content (8473238 floor); in Godot it would ride the same pattern as W10's Mojo kernel — a pure-data sim class with a presentation adapter (particles/sprites driven by sim state). Not a W6 deliverable; the register entry exists so a future Godot title doesn't go shopping for a package that doesn't exist.
5. **Reactive voice / event-coverage.** *Why:* W6 needs only the *shape* (engine events → sound table) — the full coverage system is W5's Unity subject. The Godot version, when a full title needs it, is the same custom event bus over `AudioStreamInteractive`/FMOD events; no framework provides coverage logic in this ecosystem either.
6. **Ledgers (book of record, exposure/development bookkeeping).** *Why:* canon-shaped append-only data, as in every chapter. *Rides on:* the §(e) serialisation; `Resource` data assets for authored tables (tracks, contexts), JSON for runtime state.
7. **The conformance harness itself.** *Why:* trace generation/comparison tooling (spec scripts in, per-tick state out, diff vs reference) is estate test infrastructure. *Rides on:* gdUnit4 suites + headless runs; its outputs file directly into bloch as the week's breakage/divergence log.

## Quality bar (Laplace3D-class minimum)

Identical numbers to the Unity chapter — the bar does not move with the engine:

- **60 fps presentation** in the browser build on a mid-range laptop (Compatibility renderer budget respected: no Forward+ assumptions anywhere in shared assets).
- **Motion on every frame** — idles are systems (breath/blink/look), never stills.
- **Secondary-motion lag ≤ 17 ms** behind primary motion (one frame at 60 fps).
- **Humanised jitter** — seeded, bounded micro-variation; mechanically perfect loops fail the bar.
- **Expression readability at delivery size** — the three girls' F-code sets must read at itch render size; screenshot-gated (D-221 discipline), and for W6 specifically this doubles as the decoupling evidence: the *same* cue at the *same* size must read differently per girl.
- **Seamless loops** — verified by frame-diff at the seam.
- **Audio sync ≈ +12 ms ± 25 ms** for tier-event stingers against their visual beats. Note the web-audio caveat: single-threaded exports have higher audio latency variance than threaded ones; measure in the shipped build, not the editor, and file the number.
- **Deterministic evaluation where the engine allows** — Godot's allowance, stated honestly: GDScript arithmetic on a fixed build is reproducible, and a fixed-step pure-data core with seeded RNG is deterministic *on that build*; Godot does not promise cross-platform float identity, and physics is not part of the scored core for exactly that reason. The conformance claim is therefore trace-equality against the reference within the spec's stated tolerances — and any tolerance the spec forgot to state is, by the week's own rule, a spec finding.

## Adult-content policy notes

- **Godot itself:** MIT licence, no content terms, no services layer, no telemetry gate — the engine imposes *nothing* on an adult title. There is no Godot storefront to be banned from; distribution is the game's own problem.
- **itch.io (the storefront, same as every chapter):** fictional/illustrated adult content is allowed with the "Has sensitive content" flag; sexualised imagery of real humans is prohibited; any sexual depiction of minors/minor-presenting characters is prohibited (creator FAQ as quoted in enforcement notices: https://itch.io/t/5119952/stop-with-the-radio-silence-administrators-we-need-some-kind-of-communication-on-the-nsfw-ban). Cover images should be SFW; paid adult titles have faced payment-processor-driven de-indexing since 2025 while free titles remain listed (https://itch.io/t/7081450/am-i-allowed-to-promote-18nsfw-content-in-the-release-announcements-boardforum) — jam entries are free. The 18+ gate is the game's own first screen (GJ-07); Godot provides the `Control` to build it and nothing else, which is the correct division of labour.
- **Asset-store angle:** the Godot Asset Library is a distribution channel for *addons*, not games — nothing in W6's stack needs policy clearance there. (Contrast Unity, where Asset Store *purchases* are fine but Unity's ad/services policies would matter.)

## Risks / seams

1. **Single-file template fiddliness (the named seam).** Multi-file is Godot's native shape; the single-file shell is custom work with three failure modes to burn down at preflight, in order: (i) shell loads but the inlined `.pck` isn't found by the engine loader, (ii) threading/COOP-COEP headers on itch's embed break the threaded build — mitigated by the single-threaded export, which must then be *performance-verified*, (iii) base64 bloat pushing the file over itch limits anyway. Preflight = empty project + one Spine rig + the real shell, end to end, before game work.
2. **spine-godot version matrix.** Spine version × Godot version × extension build must all agree; the editor, the runtime download, and the export templates get pinned as one unit in the project README on day one. A mid-week Godot point upgrade is a self-inflicted wound.
3. **GDExtension-on-web risk.** If the spine-godot web library misbehaves in the single-threaded export, the fallback ladder is: threaded export + PWA workaround → custom module build → sprite-based rigs for W6 with the finding filed (the finding would itself be a legitimate program result, but it is the *last* resort, not the plan).
4. **Dialogic 2 is alpha.** Pin the release; read its changelog before any bump; for a full Godot VN, budget a Dialogic-upgrade task per Godot minor version. W6's thin use is deliberate insulation.
5. **GDCubism temptation.** A Cubism-shaped shortcut into Godot exists (§b) but is community-maintained and build-it-yourself; adopting it mid-program would trade a known seam (Spine in Godot) for an unknown one. Recorded here so the decision is on file as *considered and deferred*, not overlooked.
6. **GDScript performance ceiling** is real but irrelevant at VN scale — *provided* the scored cores stay allocation-light pure classes. The moment a core starts doing per-tick scene-tree work, both performance and determinism arguments collapse; the register's architecture rule (no engine services inside evaluators) is the guard.
